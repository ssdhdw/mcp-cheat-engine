# Cheat Engine MCP GUI bridge

MCP STDIO → Python → локальный Windows named pipe → Lua внутри Cheat Engine →
`synchronize()` → реальные объекты GUI. Отдельная копия таблицы не создаётся:
агент и пользователь работают с одним `AddressList`. Добавленная запись выделяется,
изменение значения отображается в таблице, заморозка меняет обычный checkbox CE.
Отдельное окно **MCP agent activity** показывает время, операцию, короткие детали
и результат, хранит последние 200 действий. Одна операция занимает одну строку;
длинные поля сокращаются, переносы строк удаляются, автоматический перенос отключён.
Для поиска показываются этап (`scan_first`/`scan_next`), условие и значение;
для добавления/редактирования записи — адрес и значение. При чтении/записи байтов
и дизассемблировании выводится диапазон адресов без дампа. Тексты скриптов и снимки
регистров в журнал не копируются. Например:

```text
20:12:28 [add] address - 014B0F50, value - 10, type - 4 Bytes | OK
20:12:29 [value] address - 014B0F50, value - 90 | OK
20:12:30 [scan_first] exact - 98, type - 4 Bytes | OK
20:12:31 [scan_next] decreased | OK
20:12:32 [memory_read] range - 014B0F50-014B0F6F | OK
```

## Инструменты (25)

| MCP tool | Действие |
| --- | --- |
| `get_state` | PID выбранного процесса и число записей |
| `list_processes` | Процессы, доступные CE |
| `attach_process` | Выбор процесса в CE |
| `list_records` | Чтение живой таблицы, страницы до 200 записей |
| `add_record` | Создание видимой числовой записи по адресу/выражению CE |
| `set_record_value` | Запись через `MemoryRecord.Value` |
| `freeze_record` | Изменение `MemoryRecord.Active` |
| `stop_bridge` | Отключение моста до перезапуска CE |
| `first_scan` | Первый поиск: точное, больше/меньше, диапазон, неизвестное значение |
| `next_scan` | Повторный поиск, в том числе increased/decreased/changed/unchanged |
| `scan_status` | Состояние асинхронного поиска и прогресс |
| `scan_results` | Чтение результатов поиска из GUI, страницы до 200 адресов |
| `reset_scan` | Новый поиск с очисткой результатов |
| `read_memory` | Чтение до 4096 байтов по адресу/символу, переход в Memory View |
| `write_memory` | Запись байтов с проверкой исходных и чтением результата |
| `list_modules` | Модули процесса, базовые адреса, размеры, пути |
| `disassemble` | До 100 инструкций с переходом в дизассемблер GUI |
| `resolve_pointer_chain` | Разрешение цепочки указателей и её промежуточных шагов |
| `add_pointer_record` | Создание записи с цепочкой указателей в таблице CE |
| `update_record` | Переименование записи |
| `watch_memory` | Hardware breakpoint на запись, доступ или исполнение |
| `get_watch_hits` | Инструкции и снимки регистров сработавшей точки |
| `remove_watch` | Удаление точки, созданной этим MCP |
| `add_assembler_script` | Добавление неактивной записи Auto Assembler |
| `set_script_enabled` | Явное включение/выключение записи Auto Assembler |

Типы: `byte`, `word`, `dword`, `qword`, `float`, `double`. Запись/заморозка
существующих скриптов и групп через числовые инструменты отклоняется. Перед мутациями проверяется
`expected_pid`, чтобы ручное переключение процесса не перенаправило запись.
PID не защищает от повторного использования того же PID после перезапуска процесса.
Изменение значения возвращает фактически прочитанное CE значение; целевая программа
может немедленно изменить его снова. Не считайте ответ подтверждением долговременного сохранения.

Поиск запускается через настоящие поля и кнопки главного окна CE и сохраняет
родные обработчики завершения: результаты видны в GUI, ручные результаты доступны агенту.
Поддерживаются числовые типы, включая float/double. Поиск строк и AOB, автоматический
pointer scan/rescan, полный пошаговый отладчик и отдельные инструменты Mono/.NET
пока не реализованы. Произвольного `execute_lua` нет. Auto Assembler поддерживает
обычные возможности CE, включая инъекции и Lua-секции; скрипт добавляется неактивным.

## Рабочие сценарии туториала

**Известное значение:** `first_scan(expected_pid, "98", "dword")`, затем
опрашивать `scan_status`, пока `busy=false`. Прочитать `scan_results`.
После изменения значения в программе вызвать `next_scan(expected_pid, "decreased")`
или `next_scan(expected_pid, "exact", "90")`, дождаться завершения и снова прочитать результаты.
Адрес из результата можно передать в `add_record`, после чего менять или замораживать значение.

**Неизвестное значение:** `first_scan(expected_pid, value_type="dword", scan_type="unknown")`.
Это снимок регионов: до сужения списка `scan_results` выдаёт понятную ошибку.
После изменения значения вызвать `next_scan(..., scan_type="changed")` или `decreased`,
затем `unchanged`, если требуется отсеять постоянно меняющиеся значения.
Первый поиск заменяет прошлые результаты. Сканирование не блокирует GUI ожиданием
`waitTillDone` в основном потоке. Параметры диапазона по умолчанию берутся из GUI;
остальные настройки регионов/выравнивания остаются теми, что установлены в CE.
Числа count/progress возвращаются строками, чтобы не терять точность больших значений.

**Код, который меняет значение:** `watch_memory(expected_pid, address, "write", 4)`.
После ответа `armed=true` выполните действие в тестовой программе и прочитайте
`get_watch_hits`. Точка автоматически продолжает выполнение программы и хранит до 100
снимков регистров; переполнение отражается в `dropped`. Поле `ip` для data breakpoint
обычно указывает на инструкцию ПОСЛЕ записи; исследуйте соседние инструкции, прежде чем
ставить патч. Откройте нужный участок через `disassemble`. Завершите `remove_watch`.
Существующие точки пользователя не перезаписываются. Если отладчик ещё не запущен,
используется Windows debugger; hardware slots ограничены. `stop_bridge` удаляет
принадлежащие MCP точки текущей сессии, но не выключает скрипты и замороженные записи.

**Указатели:** `resolve_pointer_chain(expected_pid, "Tutorial.exe+OFFSET", [16, 4])`
выполняет `p=readPointer(base)+16`, затем `address=readPointer(p)+4`.
Порядок смещений — от базы к значению; `add_pointer_record` сам переводит его
в обратный порядок хранения CE. Результат — кандидат цепочки, переносимость
после перемещения объекта необходимо проверить отдельно.

**Патчи и инъекции:** `read_memory` возвращает hex. `write_memory` требует
`expected_hex` той же длины, отвергает несовпадение, возвращает `original`, `observed`
и `verified`. Для отката передайте сохранённые оригинальные байты, ожидая байты патча.
Проверка/запись не атомарны относительно целевого процесса. Auto Assembler-скрипты
с секциями `[ENABLE]`/`[DISABLE]` добавляются в видимую таблицу, включаются отдельным
`set_script_enabled` и там же выключаются. Наличие `[DISABLE]` не гарантирует корректный
откат: его код и исходные байты нужно проверить. Изменения GUI не означают автоматически,
что шаг Tutorial пройден — проверяйте реакцию самой программы.

## Запуск на Windows

Требуется установленный/собранный Cheat Engine с Lua API и Python 3.11+.
Пересборка CE для этого прототипа не нужна. Исходники CE собираются по инструкции
в корневом README. В fork включён готовый `Cheat Engine/bin/autorun/ce_mcp.lua`:
при запуске CE из этой папки мост стартует автоматически через штатный autorun.

1. В папке `mcp` создайте окружение и установите зависимости:

   ```powershell
   python -m venv .venv
   .\.venv\Scripts\python.exe -m pip install -r requirements.txt
   ```

2. Для установленного CE один раз установите автозапуск из PowerShell
   (для `Program Files` может потребоваться запуск PowerShell от администратора):

   ```powershell
   .\.venv\Scripts\python.exe install_autorun.py --ce-dir 'C:\Program Files\Cheat Engine'
   ```

   Перезапустите CE. Окно **MCP agent activity** появится автоматически;
   открывать Lua Engine и выполнять команды больше не нужно. Скрипт полностью
   автономный: после установки ему не требуется путь к клонированному репозиторию.
   Повторите установку после обновления моста. Отменить автозапуск:

   ```powershell
   .\.venv\Scripts\python.exe install_autorun.py --ce-dir 'C:\Program Files\Cheat Engine' --uninstall
   ```

   Удаление применяется после перезапуска CE. Уже запущенный мост можно отключить
   инструментом `stop_bridge`. Автозапуск активирует его снова при следующем запуске CE.

   Для ручного запуска без установки autorun остаётся вариант через Lua Engine:

   ```lua
   dofile([[C:\path\to\mcp-cheat-engine\mcp\ce_bridge.lua]])
   ce_mcp.start()
   ```

   Должно появиться окно журнала. Этот ручной вариант не нужен при установленном autorun.
   Для нескольких экземпляров CE используйте разные имена pipe: `ce_mcp.start('ce-mcp-2')`.

3. В конфигурации MCP-клиента укажите абсолютные пути к Python и `server.py`:

   ```json
   {
     "mcpServers": {
       "cheat-engine": {
         "command": "C:\\path\\to\\mcp\\.venv\\Scripts\\python.exe",
         "args": ["C:\\path\\to\\mcp\\server.py"],
         "env": {
           "CE_MCP_PIPE": "ce-mcp"
         }
       }
     }
   }
   ```

   Это общий пример JSON; расположение и формат настроек зависят от клиента.
   Сервер работает через STDIO и запускается самим MCP-клиентом.

## Проверка в живом GUI

На Cheat Engine Tutorial или своей тестовой программе:

1. `list_processes`, затем `attach_process(pid)` и `get_state`; проверить выбранный
   процесс в GUI.
2. Найти доступный числовой адрес средствами CE, вызвать
   `add_record(expected_pid, address, "MCP test", "dword")`.
   Проверить появление и выделение записи.
3. Передать возвращённый ID в `set_record_value`; сравнить возвращённое значение,
   колонку Value в GUI и значение в тестовой программе.
4. `freeze_record(..., true)`, затем `false`; проверить checkbox и поведение значения.
5. Вручную изменить описание/значение в CE и проверить `list_records`.
6. Вручную переключить процесс; запись со старым `expected_pid` должна завершиться ошибкой.
7. Вызвать `stop_bridge`; следующая команда должна получить ошибку соединения.

## Протокол и ограничения

Одна команда на соединение. Кадр: uint32 little-endian длина, затем payload,
максимум 1 MiB. Запрос — UTF-8 поля с percent encoding, разделённые TAB:
`operation, arguments...`. Ответ — UTF-8 JSON:
`{"ok":true,"result":...}` или `{"ok":false,"error":"..."}`.
Аутентификации нет: локальные процессы, имеющие доступ к pipe, могут вызывать
команды моста, в том числе запись памяти, отладку и включение Auto Assembler. Это локальный IPC, не удалённый сетевой сервис. Upstream
`createPipe` даёт широкий локальный ACL. Локальный процесс может занять единственное соединение
и заблокировать worker; GUI продолжит работать. Для промышленной версии нужен
собственный Pascal pipe server с ACL текущего пользователя и таймаутами чтения.

Python отменяет ожидание по дедлайну 10 секунд. Таймаут/обрыв после отправки
может означать, что команда уже выполнилась: сначала прочитайте состояние,
не повторяйте мутации автоматически. Автоматических повторов нет.
Работа синхронизирована с GUI, поэтому длительный обработчик может задержать интерфейс.
Мост не меняет прав CE: при необходимости доступа к повышенному процессу права
нужно обеспечить при запуске CE. Закрытие окна журнала скрывает его; отключайте
мост через `stop_bridge` или завершение CE. Повторный запуск требует перезапуска CE.

## Автоматические тесты

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m unittest discover -s . -p 'test_*.py' -v
```

Тесты выполняют настоящий Lua-код с подменой CE API, проверяют обращение к GUI
только через `synchronize`, Unicode/экранирование, проверку PID,
валидацию, реальный Windows named pipe и MCP initialize/list_tools/error через STDIO.
Также проверяются автоматический запуск упакованного скрипта, повторная загрузка,
установка/обновление/удаление и сохранность чужих скриптов. После изменения
`ce_bridge.lua` обновляйте копию для сборки: `python install_autorun.py --package`.
Тесты с подменой API сами по себе не подтверждают совместимость с конкретной сборкой CE.

Для живой проверки есть отдельный opt-in сценарий:

```powershell
.\.venv\Scripts\python.exe live_smoke.py --ce-exe 'C:\Program Files\Cheat Engine\cheatengine-x86_64.exe'
```

Он запускает временную копию установленного CE с отдельным pipe и собственный
Python-процесс с контролируемыми значениями. Установленный autorun, существующий
экземпляр CE и текущая программа пользователя не изменяются. Проверяются реальные
GUI-сканы dword/float/double, неизвестное начальное значение и changed/decreased,
чтение и обратимая запись, цепочка указателей, модули, дизассемблер, включение/отключение
Auto Assembler и срабатывание hardware breakpoint со снимком регистров.
Созданные тестом процессы завершаются, временная копия удаляется.
В этой среде прошли 20 автоматических тестов и 23 проверки на реальном CE,
включая чтение реального окна журнала и проверку краткости строк без дампов.
Это не утверждение о прохождении всех шагов Tutorial или визуальном качестве каждого окна.
